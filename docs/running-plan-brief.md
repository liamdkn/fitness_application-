# Running plans: planned runs vs. what actually happened on the Watch

## The ask

A running plan with a start date and weekly runs (easy, long, tempo,
interval - different types, different target distances). Liam tracks
every run on his Apple Watch and isn't changing that - runs must come
into the app from HealthKit, not manual entry. Core goal: see planned
vs. actual per run, and progress toward the plan overall (he's doing
a half marathon before a full marathon). Steps generated by a run
aren't a concern (the existing step-exclusion system already covers
that for cardio types generally - nothing new needed there).

Good news on scope: the Watch-workout detect-and-confirm pipeline
already exists and already does almost exactly this, just for walks
and stairmaster sessions, not runs yet - this is substantially an
extension of `WatchActivityViewModel`/`HealthKitManager`, not a new
subsystem. `CardioType.outdoorRun` already exists too (defined, just
never populated from HealthKit). The real gaps: nothing reads
*distance* from HealthKit at all today (not requested in
`HealthKitManager.requestAuthorization`, no column on
`cardio_tracking_sessions`), and there's no "plan" concept anywhere -
only a one-off cardio session with no relationship to a target.

## 1. HealthKit: detect runs, read distance

`HealthKitManager.swift`:
- `WatchWorkoutKind` gains a `.running` case.
- Add `private var distanceType: HKQuantityType { HKQuantityType(.distanceWalkingRunning) }`,
  include it in `requestAuthorization`'s read set (not requested
  today - needs adding).
- `DetectedWatchWorkout` gains `distanceMeters: Double?`.
- `fetchRecentWorkouts`: add `case .running: kind = .running` to the
  `workoutActivityType` switch, and populate `distanceMeters` via
  `workout.statistics(for: distanceType)?.sumQuantity()?.doubleValue(for: .meter())`
  for every kind, not just running (free to populate for walks too,
  though nothing currently reads it there - harmless).

## 2. Schema: distance on the actual side

New migration (`0056_...`): `cardio_tracking_sessions` gains
`distance_meters numeric`. `CardioSessionRepository`:
`NewHealthKitCardioSession` and `importFromHealthKit(...)` gain a
`distanceMeters: Double?` param, threaded through from the detected
workout. App-native live-tracked sessions (`NewCardioSession`/
`startSession`) leave it `nil` - per Liam, running is Watch-only, no
in-app distance entry needed for the live-tracker flow.

`WatchActivityViewModel.loadCandidates()`: add `case .running` to the
kind switch alongside `.walk`/`.stairmaster`, same dedup/overlap
checks, `built.append(.cardio(workout, cardioType: .outdoorRun))`.
No new import UI needed - it's the same confirm-to-import card the
walk/stairmaster candidates already use; just needs to display
distance when present (e.g. "5.2 km" alongside the existing duration/
heart-rate/calories line, wherever that candidate card is rendered).

## 3. New: the plan itself

Two new tables, new migration:

```sql
create table running_plans (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references auth.users(id),
  name text not null,
  start_date date not null,
  target_race_date date,
  target_distance_km numeric,
  created_at timestamptz not null default now()
);

create table planned_runs (
  id uuid primary key default gen_random_uuid(),
  running_plan_id uuid not null references running_plans(id) on delete cascade,
  date date not null,
  run_type text not null check (run_type in ('easy', 'long', 'tempo', 'interval', 'race_pace', 'rest')),
  target_distance_km numeric,
  notes text
);
```

Run type set is a proposed default, not a given - `easy` (recovery
pace, the bulk of weekly volume), `long` (the week's longest run,
builds endurance), `tempo` (sustained comfortably-hard pace, builds
lactate threshold), `interval` (short hard efforts with recovery
between, builds speed), `race_pace` (practicing the actual target
pace), `rest`/cross-train (no run, included so a plan's week is
complete without gaps). `target_distance_km` nullable since an
interval day is often defined by reps/distance-per-rep rather than a
single total (e.g. "6x400m") - `notes` is a free-text escape hatch for
that kind of detail rather than over-modeling interval structure now.

`RunningPlanRepository` (new): CRUD for a plan and its planned runs,
`fetchActivePlan()` (most recent plan whose date range covers today),
`fetchPlannedRuns(planId:)`.

## 4. Planned vs. actual

New `RunningPlanViewModel` (or folded into wherever Train tab/
`TrainingHistoryView` lives): for each `planned_run`, look up any
`cardio_tracking_sessions` row with `cardio_type = outdoor_run` whose
`started_at` falls on that same calendar date - same-day matching,
not exact-time, since a planned run is a day-level target, not a
timed slot. Display per row: type, target distance, and once a
same-day actual exists, actual distance beside it (simple delta or
percent-of-target, not a pass/fail judgement - a long run 1km short
isn't a failure, it's just informative, matching the "honest
assessment of actual progress" framing rather than gamifying it).

Overall progress: sum of actual distances across the plan so far vs.
sum of planned-to-date targets - the "how are we progressing" figure
Liam asked for, one number rather than scrolling every week.

## 5. Not solved by this brief: an actual plan to put in

Liam wants "a couple" plans put into the app - that's real training
content (a half-marathon build, specific weekly structure), not
something to invent without his actual current weekly mileage, long-
run day preference, and (if he has one) a target race date. Once the
schema/UI above exists, that's a short follow-up conversation to
populate real `planned_runs` rows, not guessed at here.

## 6. UI entry point

Natural home is alongside `TrainingHistoryView` (Train tab) given
that's where cardio/workout history already lives - a new "Running
Plan" section or its own screen reached from there, rather than a
fourth top-level tab. Flagging as a call Claude Code can make on
exact placement; not prescribing a specific screen layout here.
