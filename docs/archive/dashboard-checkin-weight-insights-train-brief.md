## 1. Daily Check-In (`Views/Checkins/DailyCheckinSheet.swift`)

1. **Weight input** — round/display to one decimal place (e.g. `72.2`). The saved value already formats to `%.1f` when *reloading* an existing entry, but the text field itself doesn't constrain what gets typed in — worth adding input filtering (or just formatting on blur) so a stray `72.23` can't get saved in the first place.
2. **Sleep prefill should stay editable — this is a real bug, not just a request.** Checked the code: when Apple Health has a sleep sample synced, the field is prefilled *and* set `.disabled(hasExistingSleepLog)` — genuinely un-editable, not just showing a placeholder. Worse, even if that were fixed, the save path only calls `healthRepository.upsertSleep(...)` when `!alreadyLogged` — so a correction typed into that field today would silently not save even after unlocking the field. Both need fixing: remove the disable, and change the save condition so a manually-entered value always writes (marking it clearly as a manual override, the same way nutrition_logs already distinguishes `source: manual` vs `healthkit`).
3. **Water in litres, not ml** — `yesterday_water_ml` stays the column (no reason to touch the schema), just change the input control to accept `2.5` and convert to ml on save / from ml on load, same pattern as weight's kg-with-decimal handling.
4. **Off-plan / alcohol** — leave as the current toggle-plus-notes for now. Liam's flagged a future version where selecting it opens a curated form to actually categorize the deviation (alcohol vs. restaurant meal vs. binge, etc.) rather than free text — parked as a V2 item, not building it now.
5. **Toolbar layout** — Save moves to top-right (where Skip currently sits, `.topBarTrailing`), Skip becomes an X icon at top-left (`.topBarLeading`).
6. **Labels** — "Energy" → "Energy Level" (the code just says "Energy"). "Soreness" is already labeled "Soreness (DOMS)" in the code — Liam's ask matches what's there, so this one's likely already done; worth a quick look before treating it as new work.
7. **9am check-in reminder notification** if the daily check-in hasn't been completed yet, with the trigger time configurable in Settings. Needs a local notification scheduled once the check-in flow knows it's due and cancelled/not-sent once completed (`CheckinAvailabilityService` already tracks `dailyCompletedToday`, which is the natural signal to check before firing). **Depends on the still-pending Notifications section of this brief** — build the check-in-specific piece, but hold off finalizing the settings UI for the time picker until that section lands, in case it changes the shape of how notification settings are organized generally.

## 3. Weekly Insights (`ViewModels/WeeklyInsightsViewModel.swift`, `Views/Dashboard/WeeklyInsightsView.swift`)

**3.1 — Adherence score as a weekly average, not a daily pass/fail sum.** Liam's instinct: a bad day balanced by a good day should net out to "the week was fine," rather than the current per-day-scored-then-summed approach. This is a real, separate design conversation (current `AdherenceScoreEngine` computes a daily score with completeness gating, per the Aug 29 work) — worth its own pass once Liam has a clearer formula in mind, not a quick edit. Flagging here so it's not lost, not solving it in this doc.

**3.2 — Steps debt vs. average steps/day: verified, and it's the opposite of what you described.** Read both calculations directly:
- `avgStepsPerDay` deliberately **excludes today** — it only sums `offset < completedDays` (fully-elapsed days), specifically so a still-accumulating day doesn't drag the average down. It's a stable, past-days-only figure.
- Steps debt (`stepsBankedTowardDebt`) deliberately **includes today's live count** if HealthKit has synced anything yet — the code comment says this explicitly, framed as "am I on track *right now*."

So it's not that steps debt is lagging a day behind — average steps/day is the one that never includes today, by design, and steps debt is the live one. If what you're seeing in the app feels backwards from that, that's worth flagging as a display bug distinct from the calculation itself (i.e., the numbers might be computed right but labeled or laid out in a way that reads as the opposite) — worth a quick side-by-side check against today's actual step count next time you look at both.

**3.3 — "Weight change" explained.** It's `last.weightKg - first.weightKg` across the weigh-ins logged within the selected week — literally the net change from your first entry that week to your last, not a fluctuation range and not a comparison to the prior week. If you only log once a week it'll usually read `nil` or near-zero (needs at least two distinct entries in the window to say anything).

## 4. Train Tab

**4.1 — The workout-save bug is a real, diagnosable bug, not a vague "something broke."** The screenshot shows `The file "default.store" couldn't be opened.` — that's SwiftData's own error text for its local offline-queue store, and the likely root cause is visible directly in the code: `OfflineWorkoutQueue` creates its `ModelContainer` with `ModelContainer(for: QueuedWorkout.self, QueuedWorkoutSet.self)`, and the newer `OfflineMealQueue` (built as part of the food-logging system) creates a *separate* `ModelContainer(for: QueuedMealEntry.self)` — **neither one passes an explicit `ModelConfiguration` with its own store location**, so both default to the same underlying `default.store` file, each declaring a different, non-overlapping schema. That's a well-known SwiftData footgun: once the second container touches the shared default store with a schema the first one didn't declare, SwiftData can refuse to open it. This lines up exactly with the timing (worked fine until the meal-logging offline queue was added, then broke on a workout edited offline). **Fix: give each queue its own explicit `ModelConfiguration` pointing at a distinct file** (e.g. `workout-queue.store` / `meal-queue.store`), so they stop colliding. This should be treated as higher priority than the rest of this list — it's data loss risk mid-workout, at the gym, which is exactly the scenario the offline queue was built to protect against.
**4.2 — Add a workout history button** at the bottom of the Train tab rather than listing every past workout on the tab itself — a dedicated screen (`WorkoutHistoryView` already exists and is presumably reachable some other way today) surfaced via a clear entry point instead of cluttering the main tab.
**4.3 — "Needs to be more exciting visually"** — noted, but this is a design/taste call rather than something to spec line-by-line here. Worth a follow-up conversation (reference apps/screenshots, like you did for the weight graph) once the functional fixes above are in, rather than guessing at a redesign now.

## 6. Dashboard update (Sep 16) — Weight card simplification + Today Checklist

Verified against the current code (`DashboardView.swift`) before writing this — the two-link-card issue from Section 0 of `weekly-log-brief.md` is already fixed (only `WeeklyLogLinkCard` remains on the Dashboard; `NutritionDebtView`/`StepsDebtView` are correctly embedded in the day card, not the weight card).

**6.1 — Weight card, trimmed to a glance card.**

Keep: today's weight, a trend indicator (up/down/stable — see threshold below), the goal line, and the existing "no weigh-ins yet" empty state. Remove from this card:

- The `W`/`M` range picker, the chart itself, and the period-average text (`weightChartSummaryText`) — this card is now a glance card, not a history browser.
- The `NavigationLink("Weigh-In History")` at the bottom — per your "we'll have that somewhere else," the cleanest home is a link from `WeeklyInsightsView` (it already deals in weight-per-week; a "Weigh-In History" link fits naturally near its weight section) rather than losing the entry point entirely. Flagging this placement as my call, not yours — easy to move if you want it elsewhere (Settings, or off the new Weekly Log week-picker in Section 6.3 below).
- The full chart/`Chart{}` block, `weightChartAxisStrideCount`, `weightChartAxisDateFormat`, `weightChartDomain`, `WeightChartRange` enum, and `weightChartPeriod`/`loadWeightChart()` — all of this was purely in service of the in-card chart being removed, so it goes with it rather than staying as dead code. `goalLinePoints` stays (still needed for the goal-line value), but its "clip to the currently paged week/month" logic (the `weightChartPeriod` references inside it) simplifies since there's no more paging — the goal line just needs today's projected value plus a recent anchor point, not a clipped range.

**Trend indicator — proposed threshold.** Daily weight is noisy (water, sodium, bowel movements), so a raw day-over-day delta will flip up/down constantly and mean nothing. Use the same pattern the nutrition-trend code already applies elsewhere in the app (a percentage compared against a fixed noise floor, whichever's larger): compare a **7-day rolling average of weight** against the 7-day rolling average from 7 days prior (i.e., this week's average vs. last week's average — mirrors how `WeeklyInsightsViewModel`'s `weightChangeThisWeekKg` already thinks in week-over-week terms), and only call it "trending up" or "trending down" if that delta exceeds **0.2kg**; anything smaller reads as "stable." 0.2kg/week is comfortably inside normal water-weight noise, so it won't flip on a bad hydration day, but it's tight enough to catch a real trend within a week or two. Needs at least 7 days of weigh-ins on each side to show anything — falls back to "not enough data yet" otherwise, same spirit as the existing "no weigh-ins yet" empty state.

**6.2 — Today Checklist.** New element at the top of the Dashboard (above the day card), three ticks:

- **Steps** — ticked when today's step count (the existing `displaySteps`, which already accounts for cardio-exclusion) meets `goal.stepTarget`.
- **Workout** — ticked when a workout (strength or cardio session) has been logged for today. Needs a quick check against however `CardioSessionMonitor`/the strength-workout save path timestamps a session — flagging this as the one item here that needs a source-of-truth check before Claude Code wires it up, rather than assuming.
- **Calories in range** — ticked when today's logged calories fall within a tolerance band of `goal.dailyCalorieTarget`, not just "under." Proposed band, same floor-plus-percentage pattern as the trend threshold above: **within 10% of target, or ±100 kcal, whichever is wider** (so a smaller calorie target, e.g. a cut, doesn't get an unreasonably tight window). Ticks whether the day landed a little over or a little under, within that band — the point is "hit the plan," not "stayed under."

**Explicitly deferred, not built now:** none of these three ticks feed `AdherenceScoreEngine` yet — you said "at a later point," so for this pass they're purely a same-day visual (green tick / empty). Worth storing the three computed booleans somewhere the future scoring work can read from cheaply (rather than recomputing), but no scoring-formula change in this pass.

**6.3 — Weigh-In History link:** see 6.1 — proposed to live on `WeeklyInsightsView` instead. See `weekly-log-brief.md` Section 6 for the related Weekly Log navigation redesign, which changes how you get to Weekly Insights in the first place.
